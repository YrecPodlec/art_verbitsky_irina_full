# Prisma — структура данных проектов

[schema.prisma](schema.prisma) описывает коллекцию MongoDB `projects`.
Один документ — один проект. Все проекты не вкладываем в один большой документ:
запрос `findMany()` возвращает массив отдельных проектов для страницы.
`media` — вложенный массив изображений конкретного проекта, не отдельная коллекция.

Схема подготовлена для установленной Prisma 6.19. Карточки подключены к серверному
запросу в [entities/project](<../app/[locale]/entities/project/README.md>).
Создание схемы и генерация клиента сами по себе не записывают данные в MongoDB.

## Первое подключение

```powershell
npm run db:generate
npm run db:check
npm run db:init
```

`db:check` только проверяет соединение и количество проектов.
`db:init` предназначен для пустой dev-базы: создаёт коллекцию со строгим правилом
type/category, применяет индексы из schema.prisma и добавляет один Майами с обложкой
из публичного Blob. Реальные размеры файла уже проверены: 2028 × 1525, WebP.
Повторный запуск не перезаписывает эту запись; при посторонних проектах останавливается.
Никакие коллекции не удаляет, существующие правила проверки сохраняет.

На момент подготовки подключения запуск остановился до изменений БД из-за DNS SRV.
Обычный DNS на компьютере не возвращал запись, публичный DNS её находил.
Сначала исправь DNS либо возьми в Atlas стандартный URI `mongodb://…` вместо SRV
и замени `DATABASE_URL` локально. Не просто удаляй `+srv`: нужны все адреса узлов
и параметры TLS/replica set/authSource из Atlas. Пароли в чат не отправляй.

Для сайта на Vercel добавь `DATABASE_URL` в Environment Variables и сделай новый
деплой. `npm run build` генерирует Prisma Client под среду сборки; локальный Windows
клиент не коммитим. Токен Blob и SDK не нужны для чтения уже публичных изображений.

## Поля Project

| Поле | Что хранит |
| --- | --- |
| `id` | Генерируемый MongoDB ObjectId; в коллекции называется `_id` |
| `slug` | Читаемая часть адреса: `miami-house` в будущем `/ru/gallery/miami-house` |
| `contentKey` | Уникальный ключ `messages.projects.<contentKey>` во всех локалях |
| `publicationStatus` | `draft`, `published`, `archived`; при создании `draft` |
| `type` | Только `residential` (жилое) или `commercial` (коммерческое) |
| `category` | Фиксированный enum `ProjectCategory`: `house`, `apartment`, `hotel`, `cafe` |
| `countryCode`, `citySlug` | Необязательные коды для фильтров; названия отображаем из messages |
| `areaM2`, `year` | Необязательные площадь числом и год проекта |
| `featured` | Редакторская подборка; не избранное пользователя |
| `coverMediaId` | Идентификатор изображения из `media`, выбранного обложкой |
| `coverPosition` | Необязательная точка кадрирования обложки; `50/50` — центр, `100/50` — правая сторона |
| `media` | Массив вложенных объектов `ProjectMedia`; для пустого проекта задаём `[]` |
| `createdAt`, `updatedAt` | Время создания и изменения, управляется Prisma |
| `publishedAt` | Время публикации, выставляет приложение, не переключается автоматически |

Стадии реализации проекта не храним. `publicationStatus` отвечает только за показ
на сайте: черновик, опубликованный или архивный проект.
Площадь и размеры изображений — данные реального объекта/файла, не размеры вёрстки.

## Тип и категория

`type` — основное направление, `category` — категория внутри него:

| type | category |
| --- | --- |
| `residential` | `house` или `apartment` |
| `commercial` | Только `hotel` или `cafe` |

`category` больше не произвольная строка: набор значений зафиксирован в Prisma enum.
Названия для посетителя находятся в `messages.projectClassification`.
Сочетания проверяет [projectClassification.ts](<../app/[locale]/entities/project/model/projectClassification.ts>):
`categoriesByType` — один справочник для клиентской формы и серверной проверки.
Типы этого справочника связаны с генерируемыми Prisma enum через `import type`.

Важно: два отдельных enum сами по себе не запрещают `residential` + `hotel`.
`isProjectClassification(value)` возвращает `true` только для разрешённой пары.
`assertProjectClassification(value)` выбрасывает `TypeError` с техническим кодом
`INVALID_PROJECT_CLASSIFICATION`, если пара неверная. Для сообщения пользователю
используем `projectClassification.errors.invalidClassification` из messages.

Проверку импортируем через публичный вход
[entities/project/classification.ts](<../app/[locale]/entities/project/classification.ts>),
который не подтягивает серверную карточку и функции next-intl:

```ts
import {assertProjectClassification} from '@/app/[locale]/entities/project/classification';

// Перед записью собираем оба итоговых поля и проверяем их вместе.
const classification = {type: nextType, category: nextCategory};
assertProjectClassification(classification);
await prisma.project.update({where: {id}, data: classification});
```

Это пример будущего кода сохранения, не уже созданный API.
При частичном обновлении отсутствующее поле берём из сохранённого проекта,
проверяем итоговую пару и записываем оба поля вместе.
Проверка отвечает только за тип/категорию, не за остальные поля проекта.
Начальный скрипт уже вызывает проверку перед созданием Майами; API редактирования пока нет.
Прямые записи через Compass не проходят через эту функцию, поэтому `db:init`
также устанавливает нативный `$jsonSchema` с `oneOf` в MongoDB, в режиме strict/error.
При расширении категорий необходимо отдельно обновить и установленный валидатор БД:
одного изменения enum и `prisma generate` недостаточно. Для наполненной базы сначала
проверь прежние документы и примени `collMod` с правилом из projectValidator.ts.

### Добавить категорию

1. Добавить код в `ProjectCategory` в schema.prisma.
2. Добавить его в нужную группу `categoriesByType`.
3. Добавить название в `projectClassification.categories` во всех JSON-локалях.
4. Обновить ожидаемые сочетания в тесте, выполнить `prisma generate` и тесты.

Для типа `residential` пока разрешены только `house` и `apartment`.
Для новой коммерческой категории необходимо явно изменить фиксированный список.

## Slug, страна и кадрирование

`slug` не заголовок и не перевод: это читаемый идентификатор адреса.
У одного проекта `slug: 'miami-house'`, а его название в JSON может быть «Дом в Майами»
или «Miami House». Смена языка не меняет slug. Пример маршрута выше ещё не реализован.

`countryCode` — страна, но в виде стандартного кода `US`, а не строки «США».
Сайт берёт название страны из `projects.<contentKey>.country` выбранной локали.
`citySlug` аналогично хранит код для фильтра, а не отображаемое название города.

`coverPosition` управляет только обрезкой обложки в карточке через `object-position`:
можно показать центр, правую сторону или другую область исходного фото.
Это не координаты объекта и не изменение файла. Без него используем центр.
Действующая карточка использует эти координаты, общие стили остаются в SCSS-модуле.

## Порядок и featured

Ручные числовые `sortOrder` и `media.order` удалены.
Изображения отображаем в порядке элементов массива `media`.
Для списка проектов предлагаем явную сортировку `createdAt` по убыванию,
затем `id` по возрастанию при совпадении дат. Без `orderBy` порядок запроса не задан.
Подборка — опубликованные проекты с `featured: true`, максимум три;
если отмечено больше трёх, выбранная сортировка определит, какие попадут в блок.
Текущий виджет передаёт фильтр и лимит в серверный запрос Prisma.

## Поля ProjectMedia

| Поле | Что хранит |
| --- | --- |
| `id` | Стабильный идентификатор изображения; можно задать вручную или получить UUID |
| `contentKey` | Ключ подписей в `projects.<project.contentKey>.media.<contentKey>` |
| `category` | `visualization`, `drawing`, `concept`, `photo` |
| `url` | Публичный URL или относительный адрес файла из `public` |
| `storageKey` | Необязательный идентификатор файла у провайдера хранения |
| `width`, `height` | Реальная ширина и высота изображения в пикселях |
| `mimeType`, `sizeBytes` | Необязательные формат и размер файла в байтах |
| `room` | Необязательный код комнаты, например `livingRoom` |

Файлы не храним в базе в виде base64 или бинарных данных. Категорию читаем из
`category`, а не определяем по пути файла. Одна галерея может фильтровать этот массив
по категориям и переиспользоваться для разных проектов.

В `url` не сохраняем временные подписанные ссылки. Приватные чертежи потребуют
отдельного защищённого механизма выдачи; нельзя публиковать их обычным URL.

## Как связаны переводы

Например, `contentKey: 'miami'` использует `projects.miami` в каждом JSON-файле.
Название, страна, город, краткое и подробное описания, история и подписи изображений
остаются в `messages`. Существующие поля карточек при этом не нужно переименовывать.
Новые поля контента добавляем одинаковыми ключами во все поддерживаемые локали.

| Ключ messages.projects.<contentKey> | Назначение |
| --- | --- |
| `name` | Заголовок проекта |
| `summary` | Краткий текст карточки |
| `description` | Описание проекта/идеи для страницы кейса |
| `story` | История проекта для страницы кейса |
| `country`, `city`, `spaceType`, `imageAlt` | Локализованные сведения текущей карточки |

**Отдельные поля `description` и `story` в Prisma не нужны** при выбранном хранении
переводов в файлах. Один `contentKey` связывает документ со всеми текстами:

```ts
const t = await getTranslations('projects');
const description = t(`${project.contentKey}.description`);
const story = t(`${project.contentKey}.story`);
```

Для `/ru/...` используется ru.json, для `/en/...` — en.json.
Ключи одинаковые, перевод каждого текста записываем вручную в соответствующий JSON.
Переключение языка выбирает словарь, а не автоматически переводит русский текст.
Поле в JSON не создаёт секцию страницы само по себе: будущая серверная страница
должна отрисовать `description` и `story`, пропуская незаполненные разделы.

В существующих трёх проектах добавлен `summary` из прежней короткой подписи,
`description` сохранён без выдуманного подробного текста, `story` пока пустой.
Заполни реальные описания и истории в обеих локалях. Карточка читает только `summary`,
поэтому длинный текст для страницы не увеличит карточку.

Для изображения с `contentKey: 'livingRoom01'` будущий адаптер читает:

```ts
t(`${project.contentKey}.media.${image.contentKey}.alt`);
t(`${project.contentKey}.media.${image.contentKey}.caption`);
```

Именно по такой структуре адаптер уже читает alt обложки; подписи пригодятся галерее.
Идентификаторы и ключи переводов не меняем при сортировке.
Добавление языка не требует изменений схемы БД, но требует JSON и регистрации локали.
Обновление JSON публикуется вместе с новым деплоем приложения.

## Пример одного документа

Условные данные для будущего `prisma.project.create({data: ...})`:
изображение по этому пути пока не создано, операция ниже не выполнялась.

```ts
const data = {
  slug: 'miami-house',
  contentKey: 'miami',
  publicationStatus: 'draft',
  type: 'residential',
  category: 'house',
  countryCode: 'US',
  citySlug: 'miami',
  areaM2: 124,
  year: 2025,
  featured: true,
  coverMediaId: 'living-room-01',
  coverPosition: {x: 50, y: 50},
  media: [
    {
      id: 'living-room-01',
      contentKey: 'livingRoom01',
      category: 'visualization',
      url: '/projects/miami-house/visualizations/living-room-01.webp',
      width: 2400,
      height: 1600,
      mimeType: 'image/webp',
      room: 'livingRoom',
    },
  ],
};
```

Поле `id` проекта и даты создания/обновления можно не передавать — Prisma их заполнит.
`publishedAt` задаём в момент публикации. Избранное пользователей в этот документ
не добавляем: позже для него потребуется отдельная связь пользователя с проектом.

## Что проверять в приложении перед сохранением

Схема задаёт типы, но не все бизнес-правила. Будущая серверная валидация должна проверять:

- Положительную площадь, ширину и высоту; допустимые год и размер файла.
- Координаты кадрирования в диапазоне 0–100.
- Корректный код страны, URL и допустимый формат ключей.
- Допустимую категорию для выбранного типа: проверка уже реализована в
  `assertProjectClassification`, её нужно вызвать в будущем обработчике записи.
- Отсутствие повторяющихся `media.id` и `media.contentKey` внутри проекта.
- Наличие выбранного `coverMediaId` среди `media.id`.
- Наличие переводов, заполненных описания/истории и доступной обложки перед публикацией.

`coverMediaId` не является настоящим внешним ключом MongoDB.
Уникальность элементов вложенного массива также не гарантируется этой схемой.
`slug` и корневой `contentKey` защищаются уникальными индексами после `db push`.
Для выдачи на сайт явно фильтруем `publicationStatus: 'published'`:
индексы не скрывают черновики автоматически.

## Команды

Из корня проекта, используя установленную Prisma:

```powershell
npx prisma format
npx prisma validate
npx prisma generate
```

Эти команды форматируют/проверяют схему и создают локальный клиент, не изменяя БД.
Конфигурация загружает `DATABASE_URL` из `.env`. Проверка схемы не доказывает,
что доступ к MongoDB работает: для неё не нужно соединение с сервером.

После проверки строки подключения и выбора базы разработки:

```powershell
npx prisma db push
```

Эта команда **меняет базу**, в частности создаёт индексы. Не запускаем её автоматически
на неизвестной базе и не используем `--accept-data-loss` или `--force-reset`.
Для MongoDB в Prisma 6 не используем `migrate dev`: прежние документы и изменение
их структуры потребуется обрабатывать отдельно. Для вложенных записей нужен replica set.

## Изменить схему

Изменяй `schema.prisma`, затем выполняй `format`, `validate` и `generate`.
Изменения индексов отдельно применяй к базе разработки через `db push`.
Переименование поля или значения enum само по себе не преобразует старые документы.
Сгенерированные файлы не правим: следующая генерация перезапишет их.

## Тесты категорий

После генерации клиента, на Node 22.18+:

```powershell
npm run test:project-classification
npm run test:projects
```

Тест проверяет все восемь сочетаний двух типов и четырёх категорий,
неполные/неизвестные входные данные, исключение при ошибке и частичные обновления.
Отдельно проверяется, что справочник покрывает все enum-значения Prisma ровно один раз.
Названия типов/категорий и сообщение об ошибке проверяются в каждой JSON-локали.
В команде используется `app/*/...`, потому что Node воспринимает `[locale]` как glob,
а не буквальное имя папки. Сами тесты расположены рядом с проверяемой функцией.
Тесты не подключаются к MongoDB и не меняют данные.
Расширенная команда также проверяет выбор обложки и JSON-правило MongoDB.
Фактическое отклонение неверных записей нужно дополнительно проверять в подключённой БД.

[вложенные типы](https://www.prisma.io/docs/orm/v6/prisma-client/special-fields-and-types/composite-types).
