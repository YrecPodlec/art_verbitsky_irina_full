# API проектов

[route.ts](route.ts) создаёт настоящий HTTP-адрес `/api/projects` внутри Next.
Это технический маршрут без `/ru` или `/en`, поэтому расположен в `app/api`.
Вся предметная логика и форма остаются в FSD-папках внутри `app/[locale]`.
Отдельный Express-сервер, порт для API и настройка CORS не нужны.

## Получить проекты

```ts
const response = await fetch('/api/projects?featured=true&limit=3');
if (!response.ok) throw new Error('Не удалось получить проекты');
const projects = await response.json();
```

Ответ — JSON-массив опубликованных проектов. Каждый содержит `contentKey`,
характеристики, ссылки и метаданные изображений, но не тексты переводов.
Клиент берёт тексты из `messages.projects.<contentKey>` выбранного языка.
Ключ подписи изображения — `messages.projects.<contentKey>.media.<image.contentKey>.alt`.

- Без параметров возвращаются максимум 30 записей, новые первыми.
- `featured=true` — только подборка, `featured=false` — остальные.
- `limit` — целое число 1–100. Пагинация пока не реализована.
- Черновики и архивные записи не возвращаются.
- `400 INVALID_QUERY` — неверные параметры.
- `503 DATABASE_UNAVAILABLE` — БД недоступна, а не пустой массив проектов.

Запросы не кэшируются, данные читаются при обращении к API.
Подборка, каталог и кейсы читают ту же БД в серверных компонентах, без лишнего
HTTP-запроса к собственному API. Этот endpoint остаётся доступным для клиентского
fetch и других потребителей. [Карта галереи](../../[locale]/(pages)/gallery/README.md).

## Добавить проект

Форма: `/ru/admin/projects` или `/en/admin/projects`.
Она вызывает `POST /api/projects`, передаёт JSON и заголовок `Authorization: Bearer <ключ>`.
Результат `201` содержит ID созданной записи, slug, contentKey и статус.
Текст проекта через API не сохраняется: он остаётся в JSON-словарях.

При открытии страницы или добавлении полей изображения записи не создаются.
Отправка только вручную. Загрузки файлов в Blob здесь нет: вставляются готовые URL.

### Включить добавление

1. Исправить `DATABASE_URL` в `.env` и доступ к MongoDB. Пароль в браузер не передаётся.
2. Сгенерировать собственный случайный ключ, например локально:

   ```powershell
   node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
   ```

3. Добавить этот ключ в серверную переменную `PROJECT_ADMIN_TOKEN` в `.env`.
   Не использовать `NEXT_PUBLIC_`, не коммитить ключ, не отправлять его в чат.
4. Перезапустить dev-сервер. На Vercel настроить обе переменные окружения и новый деплой.
5. Вставить свой ключ в поле доступа формы, заполнить данные и отправить.

Без настроенного ключа или с ключом короче 32 символов сервер запрещает все записи,
включая локальную разработку. Страница формы сама публична; защищён именно POST.
Это заготовка для одного владельца, не готовая система аккаунтов: позже заменим ключ
на вход администратора. Ключ не сохраняется в localStorage и не включается в данные проекта.

### Схема и уникальные индексы

Для уникальности `slug` и `contentKey` индексы из Prisma должны быть применены к БД.
После проверки подключения владелец отдельно запускает `npx prisma db push`.
Это изменяет структуру базы, поэтому при создании API команда автоматически не запускалась.
Не запускай `db:init`, если не хочешь добавить стартовый Майами.
Правила формы/API проверяют тип и категорию до записи даже без нативного валидатора БД.

Черновик можно сохранить без изображений и пока без JSON-переводов.
Для публикации нужны изображение и совпадающие ключи текстов и alt в ru/en.
При добавлении языка обнови проверку `entities/project/api/projectTranslations.ts`.
Изменение словарей по-прежнему требует деплоя приложения.

Ошибки POST: `400` — входные данные, `401` — неверный ключ, `403` — другой origin,
`409` — дубликат (при установленных индексах), `413` — JSON больше 128 KiB,
`415` — не JSON, `503` — доступ не настроен или БД недоступна.
Сырые ошибки Prisma, пароль и строка подключения в ответ не включаются.

## Проверки без записи в MongoDB

`npm run test:project-api` проверяет входные данные, ключ доступа и ограничение JSON.
Тесты не соединяются с MongoDB. Не вызывай успешный POST на настоящей базе для проверки,
если не хочешь создать документ. При сетевой ошибке после отправки сначала проверь Compass:
запись могла сохраниться, хотя ответ не дошёл. Автоматического повтора POST нет.
